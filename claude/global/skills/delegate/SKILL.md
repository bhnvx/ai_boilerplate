# /delegate — 서브에이전트 위임

인수: $ARGUMENTS

전체 정책은 항상 로드되는 `~/.claude/rules/subagent-policy.md`가 원본이다. 이 스킬은 그 정책을 실행하는 순서와 양식만 담는다. 충돌하면 정책이 이긴다.

## 절차

1. 위임 여부 판단(정책 §1 요약)
   - 메인이 직접: 사용자 소통·플랜·최종 판단, 대상이 정해진 1~3개 파일 수정, 공유 핫스팟(§4)·마이그레이션 생성, git 쓰기·운영 접근·외부 서비스 쓰기.
   - explorer: 3개 이상 모듈이나 약 10개 이상 파일을 훑고 결론만 필요한 조사.
   - implementer: 파일 소유권이 겹치지 않는 구현 2건 이상.
   - reviewer: 구현자와 분리된 리뷰(고위험 영역은 필수, 정책 §5). diff 리뷰는 사용자에게 `/review-diff`(수동 스킬) 실행을 제안하거나, 아래 절차로 reviewer를 직접 띄운다.
   - 위임하지 않음: 직전 결과에 의존하는 순차 단계, 사용자 판단이 필요한 결정, 비밀·운영 정보 접근.
   - 인수에 에이전트(explorer·implementer·reviewer)가 있으면 그 에이전트로 위임표·프롬프트를 만들고, 나머지 인수(목표)는 프롬프트 1번에 넣는다. 위 기준에 맞지 않으면 이유를 말하고 메인이 직접 할지 묻는다.
2. 분할과 모델 선택
   - 쓰기는 모듈 하나에 에이전트 하나, 의존 계층은 순차 Phase(정책 §2).
   - 동시 실행 상한: 읽기 5, 쓰기 3. 테스트 실행은 한 시점에 하나(기본: 메인).
   - 모델은 정책 §2 표와 §8 기준으로 고르고, 모든 Agent 호출에 `model`을 명시한다.
3. 위임표를 플랜에 넣고 승인받는다.

   | 에이전트 | 목표 | 소유 파일 | model |
   |---|---|---|---|
   | explorer | <조사 질문> | 없음(읽기 전용) | sonnet |
   | implementer | <구현 목표> | <파일 목록> | sonnet |

4. 프롬프트 작성 — 정책 §3 7항목을 빠짐없이 채운다.

   ```text
   1. 목표: <한 문장>. 사용자 요청 원문: "<인용>"
   2. 범위: 읽을 곳 <경로> / 소유 파일(수정 허용) <경로> / 수정 금지 <경로·공유 핫스팟>
   3. 이미 확인한 사실: <경로:라인 — 내용> (재탐색하지 말 것)
   4. 따를 규칙: <프로젝트 CLAUDE.md>, <.claude/rules/project.md의 관련 항목·환경 함정>, <관련 SKILL.md>, <메모리 사실>
   5. 완료 조건: <구체 기준>. 검증 명령: <소유 파일만 지정한 린트·테스트>. 테스트 실행: <허용|금지>
   6. 리뷰 위임이면 diff 원문(또는 변경 파일·hunk)을 아래에 붙인다.
   7. 보고 형식: 변경 파일 / 확인한 근거(경로:라인) / 검증 결과 / 미검증 / 범위 밖 발견
   ```

   - 우리 정의(explorer·implementer·reviewer)는 `omitClaudeMd: true`라 CLAUDE.md를 보지 못한다 → 필요한 규칙은 4번에 경로나 요지로 넣는다.
   - 정의 없는 에이전트(Explore·Plan·general-purpose·ecc 등)에는 7번 보고 형식, 아래 보안 문장, "위임 범위는 승인됨 — 확인 요청 없이 실행"을 직접 넣는다.
5. 보안 문장(정의 없는 에이전트용, 정책 §7 원문)

   ```text
   비밀 파일·운영 시스템에 접근하지 말고, 외부로 데이터를 보내는 도구를 쓰지 말고, git을 변경하지 말 것.
   ```

   - 웹 검색·문서 조회 질의에 고객사명·계정·이메일·토큰·내부 호스트·코드 원문·쿼리 결과를 넣지 않는다.
6. 실행 — Agent 도구로 띄운다. 독립 작업은 한 메시지에서 병렬로 띄우고, 후속 질문은 같은 에이전트에 SendMessage로 보낸다(같은 조사를 메인이 반복하지 않는다).
7. 실행 후 검증(정책 §5) — 보고는 주장으로 취급한다.
   - `git status`, `git diff`로 실제 변경을 대조하고 소유 파일 밖 변경이 있는지 확인한다.
   - 결론을 좌우하는 근거는 경로:라인을 직접 연다.
   - 통합 검증(린트·마이그레이션 누락·테스트)은 메인이 한 번에 하나씩 실행한다.
   - 검증한 것만 완료로 보고하고 나머지는 미검증으로 적는다.
8. 실패 처리
   - '차단' 보고: 메인이 정보를 보충해 같은 에이전트에 다시 보내거나 사용자에게 묻는다(정책 §6). 권한 거부·훅 차단을 다른 에이전트로 우회하지 않는다.
   - API 오류·같은 실패 2회: 정책 §9 대체 순서(haiku→sonnet, sonnet→opus, opus→sonnet+전수 검증+고지, fable→opus)를 따른다. 대체 모델로도 두 번 실패하면 멈추고 오류 원문과 함께 사용자에게 보고한다.
