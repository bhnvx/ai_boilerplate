# 웹 솔루션 공통 원칙 (전역)
- 언어·프레임워크와 무관하게 백엔드 API·프런트·DB 작업에 적용한다. 프로젝트 규칙이 우선한다.
- 실행 절차: 엔드포인트 작업은 `/api` 스킬을 쓰고, PR 전 점검은 사용자에게 `/preflight`(수동 스킬) 실행을 제안한다.

## API 설계
- URL은 자원 중심 복수 명사(`/orders/{id}/items`). 동작은 HTTP 메서드로 표현하고 의미를 지킨다(GET은 부작용 없음).
- 상태 코드를 일관되게: 200 성공 · 201 생성 · 204 본문 없음 · 400 잘못된 요청 · 401 미인증 · 403 권한 없음 · 404 없음 · 409 충돌 · 422 검증 실패 · 500 서버 오류(의도한 응답에 쓰지 않음).
- 에러 응답 형식은 하나로 통일한다: `code` · `message` · `details`.
- 페이지네이션·필터·정렬 규약은 프로젝트에 하나만 둔다. 목록 API는 기본 페이지 크기와 상한을 둔다.
- 버전 전략(URL `/v1` 또는 헤더)을 정하고, 깨지는 변경은 새 버전으로 낸다.
- PUT·DELETE는 멱등하게 만든다. 재시도될 수 있는 생성 요청은 멱등 키를 검토한다.
- 입력 검증은 경계(요청 스키마)에서 한다.
- 응답에 내부 전용 식별자·민감 필드(비밀번호 해시·토큰·내부 메모)를 노출하지 않는다.

## 인증·인가
- 모든 엔드포인트는 기본 인증. 공개는 명시적으로 표시한 것만.
- 인가는 서버에서 자원 소유·역할 기준으로 검사한다. 목록 조회도 소유 범위로 제한한다.
- 토큰은 만료와 갱신 흐름을 둔다.
- CORS·CSRF·쿠키(Secure·HttpOnly·SameSite) 설정은 환경별로 명시한다.

## 데이터
- 트랜잭션 경계는 서비스 계층에서 명확히 정한다.
- N+1 쿼리 금지. 반복문 안에서 쿼리하지 않는다.
- 인덱스는 실제 쿼리 패턴(WHERE·JOIN·ORDER BY) 기준으로 만든다.
- 마이그레이션:
  - 적용된 마이그레이션은 수정하지 않는다. 새 마이그레이션을 만든다.
  - 파괴적 변경은 단계로 나눈다: 추가 → 백필 → 전환 → 삭제.
  - 대용량 테이블은 잠금·실행 시간을 먼저 확인한다.
  - 생성·적용은 메인 에이전트가 사용자에게 먼저 확인한다. guard-migrations 훅은 적용 명령(auto·bypassPermissions 모드 제외)·기존 파일 수정·삭제·파괴적 변경에만 확인을 요청하고 생성은 묻지 않는다.
- 감사 컬럼(created_at 등)·소프트 삭제 관례는 프로젝트 규칙을 따른다.

## 관측
- 구조화 로그 + 요청 ID(요청 전 구간에 전파).
- 로그에 PII·비밀을 남기지 않는다.
- 헬스체크 엔드포인트를 둔다.
- 알림은 5xx·장애 신호에만 건다. 4xx는 지표로 본다.

## 설정
- 설정은 환경 변수로 주입한다. 새 키는 `.env.example`에 함께 추가한다.
- 환경별 차이는 설정 한 곳에 모은다. 코드 곳곳에 환경 분기를 두지 않는다.

## 테스트 계층
- 단위(도메인 로직) / 통합(API + DB) / E2E(핵심 사용자 흐름).
- 엔드포인트마다: 성공 · 실패(검증) · 권한(401/403) · 경계값(빈 값·null·최대).
- 외부 API는 mock. 마이그레이션은 빈 DB에 처음부터 적용해 본다.

## 프런트
- 접근성 기본: 시맨틱 마크업, 키보드 조작, 색 대비.
- API 클라이언트는 단일 모듈에 모은다(기본 URL·인증·에러 처리).
- 로딩·에러·빈 상태를 모두 처리한다.
- 공개 빌드(번들·공개 env)에 비밀을 넣지 않는다.

## 보안·성능 점검
- 요청 크기 제한, rate limit, 업로드 검증(형식·크기·저장 경로).
- 의존성 취약점을 점검한다.
- 캐시는 키와 무효화 규칙을 명시한다.

## 문서
- OpenAPI·스키마 문서를 코드와 함께 갱신한다.
- 깨지는 변경은 클라이언트 영향을 PR에 명시한다.
