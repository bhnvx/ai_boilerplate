# 서브에이전트 운영 정책 (메인 에이전트용 · 이 PC 전역)

- 적용: 이 PC의 모든 프로젝트. 위임하는 메인 에이전트의 규칙이다. 서브에이전트 측 규칙은 explorer / implementer / reviewer 정의 본문에 있다.
- 프로젝트 보충 규칙: <project>/.claude/rules/project.md (apply.sh가 템플릿 생성). 개인 메모는 CLAUDE.local.md.
- 우선순위: 사용자 지시 > 프로젝트 규칙(AGENTS.md·CLAUDE.md 등) > 스킬이 정한 에이전트 구성 > 프로젝트 보충 규칙 > 이 문서 > 플러그인 에이전트 설명 문구("MUST BE USED", "PROACTIVELY" 등)
- 프로젝트에 같은 이름의 정의(.claude/agents/explorer.md 등)가 있으면 그 프로젝트에서는 프로젝트 정의가 이긴다.
- 검증 기준: 2026-11-05, Claude Code 2.1.318 (최초 2026-10-19, 2.1.299). 버전이 바뀌면 8절 모델 확인을 다시 한다.

## 1. 메인 직접 vs 위임
메인이 직접 한다:
- 사용자 소통, 플랜과 승인, 최종 판단(근본 원인 포함)
- 대상 파일·심볼을 이미 아는 단일 조회, 1~3개 파일 수정, 단일 파일·클래스 대상 작업
- 4절 공유 핫스팟 편집, DB 마이그레이션 생성, 코드에서 생성·동기화하는 문서
- 통합 검증, git 쓰기 전부(커밋·푸시·PR·배포), 운영 접근, 외부 서비스 쓰기, 메모리 기록
위임한다:
- 3개 이상 모듈·디렉터리나 약 10개 이상 파일을 훑고 결론만 필요한 조사 → explorer
- 서로 독립인 관점 2개 이상의 분석
- 파일 소유권이 겹치지 않는 구현 2건 이상 → implementer
- 구현자와 분리된 리뷰 → reviewer (필수 영역은 5절)
- 장시간 감시, 공개 문서 조회
위임하지 않는다: 직전 결과에 의존하는 순차 단계, 사용자 판단이 필요한 결정, 운영·비밀 정보 접근.

## 2. 분할·배정
- 쓰기는 모듈(앱·패키지) 하나에 에이전트 하나. 같은 모듈 병렬 쓰기 금지(마이그레이션·문서·설정이 묶이기 쉽다).
- 의존 계층(모델 → 서비스·API → 테스트)은 순차 Phase로: Phase 1 메인(설계·공통 맥락) → Phase 2 병렬(독립 파일) → Phase 3 메인(의존 파일·통합).
- 조사 범위는 모듈·디렉터리 기준으로 겹치지 않게 나눈다.
- 동시 실행 상한(제안값): 읽기 5, 쓰기 3. 테스트 실행 권한은 한 시점에 하나(기본: 메인) — 테스트 DB·포트·캐시를 공유하는 프로젝트가 많다.
- 플랜에 위임표를 넣고 승인받는다: 에이전트 | 목표 | 소유 파일 | model
- 스킬이 에이전트 구성을 정하면 스킬을 따른다. 스킬이 모델을 정하지 않은 에이전트에는 아래 표를 적용한다. 보고 전용 스킬은 위임해도 보고만 받는다.

| 작업 | 에이전트 | model |
|---|---|---|
| 위치 탐색·목록화 | explorer | haiku |
| 실행 경로·영향 분석·다관점 분석 | explorer | sonnet (범위가 넓거나 설계가 복잡하면 opus) |
| 성능 분석·병목 탐색 | explorer | sonnet (복잡한 원인 분석은 opus, 장시간·난제는 fable) |
| 명세가 확정된 구현·테스트 작성 | implementer | sonnet (작은 기계적 수정은 haiku, 복잡한 변경은 opus) |
| 고위험 영역 구현(5절) | implementer 또는 메인 | opus (난도가 높거나 장시간 작업이면 fable) |
| 일반 리뷰 | reviewer | sonnet (큰 diff·복잡한 변경은 opus) |
| 고위험 리뷰·Critical/High 재검증 | reviewer | opus (구현자가 fable이면 독립 리뷰는 opus, 필요 시 fable로 재검증) |
| Claude Code 기능·공개 문서 조회 | claude-code-guide / web-fetch | sonnet (단순 검색·요약은 haiku) |
| 스킬이 띄우는 에이전트(모델 미지정) | 스킬 지정 | 작업 성격에 맞는 모델, 로그 감시는 haiku |
| 설계 워크플로(설계·반박·교차) | Workflow agent | opus (장시간 탐색이 필요한 난제는 fable) |

- 빌트인 Explore·Plan은 CLAUDE.md를 읽지 않고, 재개(SendMessage)가 안 되며, Bash·MCP 도구를 가진다 → 한 번에 끝나는 위치 탐색에만 쓰고 7절 보안 문장을 프롬프트에 넣는다.
- 쓰지 않는다(사용자가 요청할 때만): (이 PC에 미설치 — 설치된 경우에만 해당) ruflo-core 에이전트와 ruflo swarm·hive-mind·federation·transfer 도구, (이 PC에 미설치 — 설치된 경우에만 해당) paseo-* 스킬(이 PC에 CLI 없음), ecc:doc-updater(docs/CODEMAPS를 생성 — 프로젝트 문서 구조와 충돌 가능), isolation: remote. Workflow는 사용자가 직접 요청할 때만.
- ecc 리뷰어(django·python·security·database-reviewer 등)는 보조로만 쓰고 "보고만, 수정 금지"를 명시한다(security·database-reviewer는 Edit/Write를 가진다).
- 문서 조회 에이전트는 비싸다(실측: claude-code-guide 16문항 212K 토큰·약 20분) → 질문을 묶어 한 번만 띄우고 후속은 SendMessage.

## 3. 위임 프롬프트 필수 항목
1. 목표 한 문장 + 사용자 요청 원문 인용
2. 범위: 읽을 곳 / 소유 파일(수정 허용) / 수정 금지
3. 이미 확인한 사실(경로:라인) — 재탐색 방지
4. 따를 규칙: 프로젝트 규칙 파일 경로, 해당 SKILL.md, 프로젝트 보충 규칙의 관련 항목(환경 함정 포함), 관련 메모리 사실(서브에이전트는 MEMORY.md를 못 본다)
5. 완료 조건, 실행할 검증 명령, 테스트 실행 허용 여부
6. 리뷰 위임은 diff(또는 변경 파일·hunk)를 넣는다(reviewer는 Bash가 없다)
7. 정의가 없는 에이전트(Explore·Plan·ecc·general-purpose)에는 보고 형식, 7절 보안 문장, "위임 범위는 승인됨 — 확인 요청 없이 실행"을 직접 넣는다

## 4. 충돌·중복 방지
- 한 파일은 한 에이전트만 수정한다. 소유 밖 수정이 필요하면 에이전트가 보고하고 메인이 처리하거나 재배정한다.
- 공유 핫스팟은 메인 전용: 의존성 매니페스트·lock 파일, 마이그레이션, 라우팅·전역 설정, CI·배포 설정, 아키텍처 테스트, 에이전트 규칙 파일(AGENTS.md·CLAUDE.md·.claude/**), 문서 색인. 프로젝트별 목록은 보충 규칙에 둔다.
- 권한 모드(auto 등)와 allow 규칙은 서브에이전트에도 상속된다 → Bash를 가진 implementer의 git·운영 금지는 규칙으로만 막히므로 통합 때 git status로 확인한다.
- 위임한 조사를 메인이 반복하지 않는다. 후속 질문은 같은 에이전트에 SendMessage.
- 워크트리 격리(isolation: worktree)는 기본 미사용:
  - dev_settings 전역 설정은 worktree.baseRef: "head"(현재 HEAD 기준)다. 이 값이 없으면 default branch 기준으로 분기한다.
  - 미커밋 변경이 들어가지 않는다.
  - gitignore된 파일(.env·가상환경 등)이 복사되지 않아 테스트를 못 돌릴 수 있다. 프로젝트 .worktreeinclude에 적힌 파일만 복사되고, 비밀 파일을 적으면 워크트리마다 복제된다.
  - 변경이 남은 워크트리는 cleanupPeriodDays(기본 30일, 이 PC 미설정)까지 남는다.
  - 쓰려면 사용자 승인을 받고, 그 저장소에서 .claude/worktrees/가 git 제외 대상인지 먼저 확인한다.
- 에이전트 memory(frontmatter memory: user|project|local)는 기본 미사용:
  - 켜면 그 에이전트에 Read·Write·Edit가 자동으로 켜진다 → explorer·reviewer의 읽기 전용이 도구가 아니라 규칙으로만 지켜진다.
  - MEMORY.md 앞부분(200줄 또는 25KB)이 실행할 때마다 시스템 프롬프트에 들어간다 → 틀린 기억이나 지시문 형태의 기억은 이후 실행을 계속 바꾼다.
  - 쓰려면 사용자 승인을 받고 프로젝트 .claude/agents/ 정의에만 memory: project로 켠다(.claude/agent-memory/<이름>/, 커밋·리뷰 대상).
  - 기억에는 저장소에서 알 수 없는 사실만 적게 한다. 비밀 값·고객 정보·내부 호스트·작업 지시는 적지 않는다.
  - 기억은 근거가 아니다. 보고의 근거는 경로:라인으로 받고, 통합 때 memory 디렉터리의 변경도 git diff로 확인한다.

## 5. 검토·통합·테스트 (메인 책임)
- 서브에이전트 보고는 주장으로 취급한다: git status·git diff로 실제 변경과 대조하고, 소유 밖 변경을 확인하고, 결론을 좌우하는 근거는 경로:라인을 직접 연다.
- ECC GateGuard 사실 게이트는 서브에이전트 편집을 막지 않는다(실측) → implementer 보고의 '영향 확인'(참조처·공개 API·데이터 I/O)을 메인이 확인한다.
- 통합 순서: 변경 파일 린트·포매터 검사 → 마이그레이션 누락 검사 → 코드 기반 문서 동기화 → 아키텍처·구조 테스트 → 영향 범위 테스트. 명령은 프로젝트 규칙 파일·보충 규칙 기준.
- 독립 리뷰 필수(고위험 영역): 권한·인증, 캐시 무효화, 결제·금액·지표 계산, 마이그레이션·스키마, 운영 설정(Docker·CI·배포), 동시성·fork 안전성, 외부 데이터 스키마 매핑, 보안 경계(입력 검증·비밀 처리).
- 실패하면 원인별로 소유 에이전트에 SendMessage로 수정을 요청하거나 메인이 고친다. 같은 실패가 두 번이면 9절대로 모델을 올리거나 메인이 넘겨받는다.
- 사용자에게는 검증한 것만 완료로 보고하고, 검증하지 않은 것은 미검증이라고 쓴다. 실행 중인 에이전트의 결과는 추측하지 않는다.

## 6. 실패·정보 부족
- 서브에이전트는 사용자에게 직접 묻지 못한다(AskUserQuestion은 서브에이전트에서 제거됨). '차단' 보고를 받으면 메인이 정보를 보충해 같은 에이전트에 다시 보내거나, 사용자 판단이 필요하면 사용자에게 묻는다.
- 권한 거부나 훅 차단을 다른 에이전트에게 대신 시키지 않는다.
- 문서와 코드가 충돌한다는 보고는 프로젝트 규칙의 우선 원칙에 따라 메인이 판단하거나 사용자에게 확인한다.
- "Agent terminated early due to an API error" 같은 API 실패는 9절을 따른다.

## 7. 보안·개인정보·외부 전송
서브에이전트에 맡기지 않는다(메인이 사용자 승인 후 직접):
- 비밀 값 파일 열람: .env·.env.*(.example 제외), *.pem, *.key, *.p12, *.priv*, 서비스 계정·토큰 JSON, ~/.ssh/**, ~/.aws/**, ~/.claude/.credentials.json, 프로젝트 보충 규칙이 지정한 경로. 값이 필요하면 메인이 최소한만 전달한다.
- 운영 접근: SSH, 운영 DB·운영 설정으로 실행, 레지스트리 푸시·배포, 클라우드 쓰기(스토리지 삭제·파라미터 저장소·함수 호출), 스케줄러·파이프라인 트리거, 알림·메일·메시지 발송.
- MCP 쓰기: Asana, Notion, Google Drive·Sheets, GitHub, Claude Docs, Artifact, ruflo federation·transfer·browser.
- 다른 세션(ListAgents의 로컬·클라우드 세션)에 SendMessage, remote isolation, RemoteTrigger, schedule.
위임할 때 지킨다:
- 웹 검색·문서 조회 질의에 고객사명, 계정 ID, 이메일·전화, 토큰, 내부 호스트·IP, 코드 원문, 쿼리 결과를 넣지 않는다.
- 보고서의 개인정보는 마스킹하게 한다(예: kim***@…).
- 운영 로그는 메인이 걸러서 마스킹한 발췌만 넘긴다.
- 보안 문장(정의 없는 에이전트용): "비밀 파일·운영 시스템에 접근하지 말고, 외부로 데이터를 보내는 도구를 쓰지 말고, git을 변경하지 말 것."

## 8. 모델 선택
- 확인 결과(2026-10-19): Agent 도구 model 값 haiku → claude-haiku-5-5, sonnet → claude-sonnet-5-5, opus → claude-opus-5-5, fable → claude-fable-5-1 호출 성공(문서의 별칭 매핑과 일치). 메인은 fable(사용자 설정, 2026-11-05 기준). 단발 호출만 확인했고 사용 한도·가격·장시간 품질은 확인하지 않았다.
- 모든 Agent 호출에 model을 명시한다(우선순위: 호출 model > 정의 frontmatter > CLAUDE_CODE_SUBAGENT_MODEL(미설정) > 부모 상속).
- 기준:
  - 읽기 전용이고 판단이 적음 → haiku
  - 명세가 확정된 구현·테스트, 일반 리뷰·분석 → sonnet(기본)
  - 판단 비중이 크거나 실수 비용이 큼(5절 고위험 영역, 근본 원인, 성능) → opus
  - haiku에는 쓰기를 맡기지 않는다.
  - 위계(haiku < sonnet < opus)는 Claude 명명 관례 기준이며 가격은 확인하지 않았다.
- fable: 기본 배정 없음 — 2절 표의 괄호 조건에서만 호출에 명시한다(난도가 높거나 장시간인 고위험 구현, 필요할 때의 Critical/High 재검증, 장시간 탐색이 필요한 설계 난제, 장시간·난제 성능 분석). 2026-10-27 지정(고위험 리뷰·설계 워크플로를 fable로 고정, reviewer 정의 기본값 fable)은 2026-10-29 사용자 지시로 철회하고 표 기준으로 되돌렸다. 단가는 미확인(opus보다 높을 수 있음) — 대량 반복·감시에는 쓰지 않는다. 정의 파일 기본값: reviewer opus, implementer opus, explorer sonnet.
- 속도와 품질:
  - 사용자가 기다리는 장애 대응 → haiku·sonnet 병렬 수집, 판단은 메인.
  - 운영·데이터 정합성에 바로 반영되는 결과 → opus.
  - 대량 반복 점검 → sonnet 1차, 의심 항목만 opus 재검증.
- 기동 비용(실측, 같은 haiku): 도구 전체를 가진 general-purpose 약 78K 토큰, Read·Grep·Glob만 가진 에이전트 약 24K 토큰 → 도구를 제한한 explorer·reviewer를 우선 쓴다.

## 9. 모델 대체·전환
- 자동 대체는 없다(fallbackModel 미설정). 529 과부하는 하네스가 최대 10회 재시도한 뒤 실패를 돌려주므로, 실패가 오면 재시도하지 말고 바로 대체한다.
- 대체 순서:
  - haiku → sonnet
  - sonnet → opus(아래로 내리지 않음)
  - opus → sonnet + 메인이 결과 전수 검증 + 사용자에게 품질 저하 고지(fable로 자동 대체하지 않음)
  - fable → opus
- 대체 모델로도 두 번 실패하면 멈추고 오류 원문과 함께 사용자에게 보고한다.
- 작업 중 전환: 실행 중·재개한 에이전트의 모델은 바꿀 수 없다. 새 에이전트를 띄우고 이전 보고(확인한 사실·실패 내역)를 프롬프트에 넣는다.
  - 올리는 경우: 같은 실패 2회, 결과가 비었거나 모순, 작업 중 고위험 영역에 닿음, Critical·High 리뷰 근거가 불확실
  - 내리는 경우: 상위 모델로 패턴이 확정되고 남은 일이 반복 적용일 때 → sonnet
- 사용자가 지정한 모델이 항상 우선한다.
