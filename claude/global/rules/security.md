# 보안 규칙 (전역)

## 비밀 파일
- 전체 목록은 guard-secrets 훅이 강제한다: `~/.claude/hooks/lib/secret-patterns.txt` + 훅 안의 경로 규칙.
- `~/.claude/settings.json`의 Read deny는 그중 핵심(.env 주요 변형·키·인증서·SSH·클라우드 자격 증명·CLI 도구 토큰)만 네이티브로 강제한다. `.env.*` 전체를 deny하면 `.env.example`까지 막히기 때문이다.
- 한쪽을 바꾸면 다른 쪽도 검토한다(dev_settings 저장소에서 고친 뒤 재설치).
- 비밀 파일(.env·.env.*(.example·.sample·.template·.dist 제외)·`*.env`, 키·인증서, 서비스 계정·토큰 JSON, ~/.ssh·~/.aws·~/.config/gh 등)을 열거나 출력하지 않는다.
- 값이 필요하면 사용자에게 최소한만 요청한다. 직접 찾아 읽지 않는다.

## 비밀·개인정보 취급
- 비밀·PII를 로그·보고·커밋·PR 본문에 넣지 않는다.
- 꼭 필요하면 마스킹한다: 이메일 `kim***@…`, 토큰은 앞 4자 + `…`.
- 비밀을 코드에 하드코딩하지 않는다. 환경 변수나 Secrets Manager 같은 비밀 저장소를 쓴다.

## 운영 접근
- 다음은 하지 않는다. 필요하면 사용자 승인 후 메인 에이전트가 직접 한다:
  - SSH, 운영 DB 접속, 운영 설정으로 실행
  - 배포·레지스트리 푸시, 클라우드 쓰기
  - 스케줄러·파이프라인 트리거, 알림·메일·메시지 발송

## 외부 전송
- 웹 검색·MCP 쓰기·Artifact 게시에 고객명, 계정 ID, 코드 원문, 쿼리 결과를 넣지 않는다.

## 차단 대응
- 권한 거부·훅 차단을 우회하지 않는다. 다른 명령이나 다른 에이전트로 돌아가지 않는다.
- 차단 사실과 사유를 그대로 사용자에게 보고한다.

## 설치·의존성
- `curl … | sh`·`wget … | bash` 같은 원격 스크립트 직접 실행 금지.
- 의존성 추가·변경은 사용자 확인 후 한다.

## 코드 기본값
- 외부 입력은 경계에서 검증한다(타입·길이·범위·형식).
- 권한 검사는 서버에서 기본으로 한다. 클라이언트 검사에 의존하지 않는다.
